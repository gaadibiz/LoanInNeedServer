## � Technical Implementation Details

### 1. Referral System & Security (HMAC)
The referral tracking system uses a cryptographic signature to prevent tampering.

*   **Algorithm:** HMAC-SHA256
*   **Key Management:** 
    *   Each partner is assigned a unique 32-byte `secretKey` during registration.
    *   This key is encrypted (AES-256) before storage in the PostgreSQL `Partner` table.
*   **Link Generation:**
    *   **Payload:** `${partnerId}|${timestamp}`
    *   **Signature:** `HMAC_SHA256(payload, decryptedSecretKey)`
    *   **URL Structure:** `/signup?pid=[ID]&ts=[TIMESTAMP]&sig=[HEX_SIGNATURE]`
*   **Validation:** 
    *   When a user clicks the link, the backend re-computes the signature using the claimed `pid` and `ts`.
    *   If the computed signature matches the `sig` param, the link is valid.

### 2. Attribution Flow (Frontend ↔ Backend)
*   **Capture (Frontend)**: 
    *   Component: `ReferralTracker.tsx`.
    *   Logic: Detects `pid`, `ts`, `sig` in URL. Stores them in `localStorage` key `lin_attribution`.
    *   Persistence: Data persists even if the user navigates away and comes back to register later.
*   **Submission**: 
    *   During registration (`lib/api.ts`), the `lin_attribution` object is retrieved and injected into the user registration payload.
*   **Processing (Backend)**: 
    *   `registerUser` controller validates the signature again.
    *   Creates `User` record with `attributedPartnerId`.
    *   Logs the event in `AttributionLog` table for auditing.
